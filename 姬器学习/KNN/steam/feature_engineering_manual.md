# Steam 游戏口碑 KNN 项目特征工程手册

## 1. 特征工程的作用

特征工程就是把原始数据转换成机器学习模型可以理解的数值特征。

本项目使用的是 KNN 算法。KNN 的核心思想是：如果两个样本在特征空间中的距离很近，那么它们可能属于相同类别。因此，特征工程会直接影响 KNN 的效果。

原始 Steam 数据中既有数值字段，也有文本字段、列表字段和索引字段，不能直接输入模型。项目中需要先完成以下处理：

```text
原始 JSON 列表
-> 字段解析
-> 索引还原
-> 数据清洗
-> 目标标签构造
-> 数值特征构造
-> 文本列表 multi-hot 编码
-> 特征标准化
-> 输入 KNN 模型
```

## 2. 原始字段示例

原始 JSON 中一条游戏数据类似：

```json
["Counter-Strike 2", 2012, 87, 8815087, 0.0, 1, [1, 8], [28, 18, 22, 2], "Valve"]
```

它对应的字段含义是：

| 位置 | 原始值 | 字段含义 |
|---:|---|---|
| 0 | `"Counter-Strike 2"` | 游戏名称 |
| 1 | `2012` | 发行年份 |
| 2 | `87` | 好评率 |
| 3 | `8815087` | 评论数量 |
| 4 | `0.0` | 价格 |
| 5 | `1` | 口碑等级索引 |
| 6 | `[1, 8]` | 游戏类型索引列表 |
| 7 | `[28, 18, 22, 2]` | 游戏标签索引列表 |
| 8 | `"Valve"` | 开发商 |

其中第 5、6、7 个字段不是直接文本，而是索引。它们需要分别去 JSON 顶层的 `ratings`、`genres`、`tags` 列表中查找真实含义。

## 3. 目标标签构造

原始口碑等级比较细，例如：

```text
Overwhelmingly Positive
Very Positive
Mostly Positive
Positive
Mixed
Mostly Negative
Negative
Very Negative
Overwhelmingly Negative
```

如果直接做 9 分类，任务会比较复杂，而且有些类别样本较少。为了让课程项目更容易讲清楚，代码将原始口碑等级合并成 4 类：

| 原始等级 | 合并后类别 |
|---|---|
| Overwhelmingly Positive / Very Positive | `highly_positive` |
| Mostly Positive / Positive | `positive` |
| Mixed | `mixed` |
| Mostly Negative 及更低 | `negative` |

对应代码逻辑：

```python
def rating_group(rating_index):
    if rating_index <= 1:
        return "highly_positive"
    if rating_index <= 3:
        return "positive"
    if rating_index == 4:
        return "mixed"
    return "negative"
```

这里要注意：`positive_rate` 和原始 `rating_index` 没有作为输入特征使用。它们只用于生成目标标签和可视化分析。原因是它们本身就和答案高度相关，如果直接输入模型，相当于把答案提前告诉模型，会导致结果虚高。

## 4. 基础数值特征

### 4.1 发行年份 `release_year`

发行年份来自原始字段，例如：

```text
2012
```

它可以反映游戏所处的年代。老游戏和新游戏在价格策略、评论积累、玩家群体方面可能存在差异。

### 4.2 价格 `price`

价格来自原始字段，例如：

```text
0.0
```

价格可能影响玩家评价。免费游戏和付费游戏面对的玩家预期不同，高价游戏往往会被玩家用更严格的标准评价。

### 4.3 评论数量 `review_count`

评论数量来自原始字段，例如：

```text
8815087
```

评论数可以反映游戏热度。但是这个字段不适合直接使用，因为不同游戏之间评论数差距非常大。

例如：

| 游戏类型 | 评论数量 |
|---|---:|
| 小众游戏 | 几百条 |
| 普通游戏 | 几千到几万条 |
| 热门游戏 | 几十万到几百万条 |

如果直接使用原始评论数，KNN 的距离计算会被这个字段严重影响。因此项目中使用了评论数的对数形式。

## 5. 评论数对数特征 `log_review_count`

代码中使用：

```python
log_review_count = math.log1p(review_count)
```

`log1p(x)` 等价于：

```text
log(1 + x)
```

这样做的目的是压缩评论数量的差距。

| 原始评论数 | 取对数后大约 |
|---:|---:|
| 100 | 4.62 |
| 1,000 | 6.91 |
| 100,000 | 11.51 |
| 8,815,087 | 15.99 |

可以看到，原始评论数之间的差距可能是几万倍，但取对数之后差距会变得更温和。

这对 KNN 非常重要，因为 KNN 依赖距离计算。如果某个特征数值特别大，它会过度影响最终距离。

## 6. 游戏年龄特征 `game_age`

代码中使用：

```python
game_age = CURRENT_YEAR - release_year
```

如果当前年份是 2026，游戏发行于 2012，那么：

```text
game_age = 2026 - 2012 = 14
```

`release_year` 表示“哪一年发行”，而 `game_age` 表示“距离现在多久”。后者对人来说更加直观。

这个特征可以帮助模型捕捉：

- 老游戏是否更容易积累评论。
- 新游戏是否更容易受到近期热度影响。
- 不同年代游戏的评分分布是否存在差异。

严格来说，`release_year` 和 `game_age` 包含的信息有一定重复。但在课程项目中，保留二者可以帮助展示特征构造思路。

## 7. 是否免费特征 `is_free`

代码中使用：

```python
is_free = 1 if price <= 0 else 0
```

含义是：

| 条件 | `is_free` |
|---|---:|
| 价格等于 0 | 1 |
| 价格大于 0 | 0 |

虽然已经有 `price` 特征，但“免费”和“付费”本身是一个非常重要的状态。

免费游戏和付费游戏的评价逻辑可能不同：

- 玩家评价免费游戏时，可能更宽容。
- 玩家评价高价游戏时，预期可能更高。
- 免费游戏往往更容易获得大量玩家和评论。

因此，`is_free` 是一个简单但有解释性的二值特征。

## 8. 类型数量特征 `genre_count`

游戏类型字段是一个列表，例如：

```text
Action, Free To Play
```

代码中使用：

```python
genre_count = len(genres)
```

如果一个游戏有两个类型：

```text
genre_count = 2
```

这个特征表示游戏被归入了多少个大类型。

它的含义可以理解为：

- 类型越多，游戏内容可能更综合。
- 类型越少，游戏定位可能更明确。

这个特征不能说明具体是什么类型，但它从列表字段中提取出了一个简单的数值信息。

## 9. 标签数量特征 `tag_count`

标签字段也是一个列表，例如：

```text
FPS, Shooter, Multiplayer, Action
```

代码中使用：

```python
tag_count = len(tags)
```

如果一个游戏有四个标签：

```text
tag_count = 4
```

这个特征表示一个游戏拥有多少个标签。

它可以反映：

- 游戏描述是否丰富。
- 游戏特征是否多样。
- 数据中关于该游戏的标签信息是否充分。

不过，`tag_count` 只能表示数量，不能表示标签具体含义，所以后面还需要 multi-hot 编码。

## 10. 开发商作品数量 `developer_game_count`

代码先统计每个开发商在数据集中出现了多少次：

```python
developer_counts = Counter(row["developer"] for row in rows)
```

然后为每条游戏添加：

```python
developer_game_count = developer_counts[row["developer"]]
```

这个特征表示：

```text
该开发商在数据集中有多少款游戏。
```

它可能间接反映：

- 开发商是否经验丰富。
- 开发商是否属于大型厂商。
- 开发商作品数量是否和口碑稳定性有关。

当然，这个特征只是一个间接信号。作品数量多并不一定代表质量高。

## 11. 类型 multi-hot 编码

原始类型字段是文本列表，例如：

```text
Action, Free To Play
```

KNN 不能直接处理文本，所以需要把文本转换成数值。

代码先统计最常见的前几个类型：

```python
top_genres = top_values(clean_rows, "genres", TOP_GENRES)
```

然后为每个热门类型建立一列：

```text
genre_Indie
genre_Action
genre_Casual
genre_Adventure
genre_Simulation
...
```

如果某个游戏拥有该类型，对应列记为 1；否则记为 0。

例如 Counter-Strike 2 的类型是：

```text
Action, Free To Play
```

那么它的编码可能是：

| 特征 | 值 |
|---|---:|
| `genre_Indie` | 0 |
| `genre_Action` | 1 |
| `genre_Casual` | 0 |
| `genre_Free To Play` | 1 |

这种编码方式叫 multi-hot 编码。

它和 one-hot 的区别是：

| 编码方式 | 特点 |
|---|---|
| one-hot | 一条数据只能有一个类别为 1 |
| multi-hot | 一条数据可以有多个类别为 1 |

因为一个游戏可以同时属于多个类型，所以这里使用 multi-hot 更合适。

## 12. 标签 multi-hot 编码

标签字段 `tags` 也使用类似方法处理。

代码先选出最常见的前 `TOP_TAGS` 个标签：

```python
top_tags = top_values(clean_rows, "tags", TOP_TAGS)
```

然后为每个热门标签建立一列：

```text
tag_Indie
tag_Casual
tag_Action
tag_Adventure
tag_Strategy
...
```

如果游戏有这个标签，该列为 1，否则为 0。

标签 multi-hot 编码的作用是：

```text
把文本标签转换为 KNN 可以计算距离的数值特征。
```

## 13. 为什么不编码所有标签

理论上，可以把所有标签都做 multi-hot 编码。但本项目没有这么做，而是只选取出现频率最高的一部分标签。

原因主要有两个。

第一，特征维度会过高。

如果有几百个标签，就会生成几百个新特征。KNN 预测时需要计算距离，维度越高，计算越慢。

第二，数据会变得稀疏。

大多数游戏只拥有少数标签。如果一共有 500 个标签，一个游戏可能只有 4 个标签，那么它的编码向量中绝大多数位置都是 0：

```text
[0, 0, 0, 1, 0, 0, ..., 1, ..., 0]
```

这种高维稀疏特征对 KNN 不太友好。因为在高维空间中，样本之间的距离可能变得不够稳定，模型效果反而可能下降。

因此，只选择高频类型和高频标签是一种折中方案：

```text
保留最常见、最有代表性的信息，同时控制特征数量。
```

## 14. 特征标准化

KNN 是基于距离的算法。假设使用欧氏距离：

```text
distance = sqrt((x1 - y1)^2 + (x2 - y2)^2 + ...)
```

如果不同特征的数值范围差异很大，距离会被范围大的特征主导。

例如：

| 特征 | 数值范围 |
|---|---|
| `price` | 0 到几十 |
| `game_age` | 0 到二十左右 |
| `log_review_count` | 4 到 16 左右 |
| `is_free` | 0 或 1 |
| multi-hot 特征 | 0 或 1 |

为了让不同特征在距离计算中更加公平，项目使用 Z-score 标准化：

```text
标准化后的值 = (原始值 - 平均值) / 标准差
```

代码中先用训练集计算均值和标准差：

```python
means, stds = fit_scaler(train_x)
```

再分别转换训练集和测试集：

```python
train_x = transform(train_x, means, stds)
test_x = transform(test_x, means, stds)
```

注意：测试集必须使用训练集的均值和标准差，不能单独用测试集重新计算。这样可以避免测试集信息泄露到训练过程中。

## 15. 最终输入模型的特征

最终进入 KNN 的特征大致包括：

| 特征 | 类型 | 含义 |
|---|---|---|
| `release_year` | 数值 | 游戏发行年份 |
| `game_age` | 数值 | 游戏距离当前年份多久 |
| `log_review_count` | 数值 | 评论数取对数 |
| `price` | 数值 | 游戏价格 |
| `is_free` | 二值 | 是否免费 |
| `genre_count` | 数值 | 类型数量 |
| `tag_count` | 数值 | 标签数量 |
| `developer_game_count` | 数值 | 开发商作品数量 |
| `genre_xxx` | multi-hot | 是否属于某个热门类型 |
| `tag_xxx` | multi-hot | 是否包含某个热门标签 |

这些特征共同构成了每个游戏的数值表示。

## 16. 特征工程的优点

这套特征工程有几个优点：

1. 逻辑清楚，适合课程汇报。
2. 没有使用过于复杂的算法，初学者容易理解。
3. 从原始 JSON 到模型输入的每一步都可解释。
4. 对文本列表字段做了基础编码，体现了数据预处理能力。
5. 对评论数做了对数处理，避免极端大数值影响 KNN 距离。
6. 对全部特征做了标准化，符合 KNN 对特征尺度敏感的特点。

## 17. 特征工程的不足

这套方案也有明显不足，汇报时可以主动说明。

### 17.1 文本语义没有被真正理解

multi-hot 编码只能表示标签是否出现，不能理解标签之间的语义关系。

例如：

```text
FPS 和 Shooter 语义上比较接近
Racing 和 Puzzle 差距较大
```

但是 multi-hot 编码不知道这些关系。它只知道某个标签列是 0 还是 1。

### 17.2 可用特征偏少

数据集中没有游戏简介、玩家评论文本、在线人数、发行商、更新频率、游玩时长等信息。

这些信息都可能影响游戏口碑，但当前项目无法使用。因此模型只能基于有限信息进行预测。

### 17.3 标签只选取高频部分

为了控制维度，项目只选择了最常见的一部分类型和标签。这会丢失一些低频但可能有用的信息。

### 17.4 KNN 不太适合高维稀疏特征

类型和标签经过 multi-hot 编码后，会产生很多 0/1 特征。如果维度继续升高，KNN 的距离计算可能变得不稳定。

### 17.5 时间特征存在一定重复

`release_year` 和 `game_age` 都表达时间信息。二者有一定重复。课程项目中保留它们是为了展示特征构造思路，但如果进一步优化，可以只保留其中一个。

## 18. 可以继续改进的方向

后续可以从以下方向改进：

1. 增加更多特征，例如发行商、折扣信息、在线人数、玩家评论文本。
2. 使用 TF-IDF 表示标签和文本，而不是简单 multi-hot。
3. 使用词向量或文本嵌入，让模型理解标签之间的语义相似度。
4. 对比其他模型，例如朴素贝叶斯、逻辑回归、随机森林。
5. 进一步处理类别不平衡问题，例如重新采样或调整评价指标。

## 19. 汇报总结模板

可以在汇报中特别强调下面这段：

```text
本项目的特征工程重点不是追求最高准确率，而是把原始 JSON 数据一步步转换成 KNN 可以使用的数值特征。

其中最重要的处理有三点：
第一，把原始索引字段还原成可读的类型和标签；
第二，把评论数、价格、年份等字段加工成更适合距离计算的数值特征；
第三，把多标签文本字段转换成 multi-hot 编码，并在训练前做标准化。

由于 KNN 依赖距离计算，所以特征尺度和编码方式会直接影响模型效果。这也是本项目选择把数据预处理和可视化作为主要亮点的原因。
```
